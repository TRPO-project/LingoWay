# LingoWay

Веб-платформа для изучения английского языка: программы обучения, уроки, база готовых материалов и генерация упражнений по собственному тексту пользователя.

Учебный командный проект по дисциплине «Теория разработки ПО».

## Стек

| Часть | Технологии |
|---|---|
| Бэкенд | Go, Gin, GORM, PostgreSQL |
| Фронтенд | HTML, CSS, JavaScript, Vite |
| Инфраструктура | Docker, nginx, GitHub Actions |

## Что понадобится для запуска

- [Git](https://git-scm.com/)
- [Docker Desktop](https://www.docker.com/products/docker-desktop/)
- [Go](https://go.dev/dl/) версии 1.27 или новее (проверка: `go version`). Нужен только для способа А

## Подготовка

```bash
git clone https://github.com/TRPO-project/LingoWay.git
cd LingoWay
```

Создайте файл с настройками из примера:

```bash
cp .env.example .env
```

Значения по умолчанию подходят для локального запуска. PostgreSQL 16 запускается в Docker и при первом старте создаёт БД из `DB_NAME` с пользователем и паролем из `DB_USER` и `DB_PASSWORD`.

Для запуска бэкенда с уже существующей внешней PostgreSQL БД Docker не нужен: заранее создайте БД и пользователя, задайте адрес подключения в `DATABASE_URL` и выполните `go run ./cmd` из каталога `backend`.

## Запуск

Выберите один из двух способов.

### Способ А: база в Docker, бэкенд запускается локально (для разработки)

```bash
# Терминал 1: база данных
docker compose up db

# Терминал 2: бэкенд, после готовности PostgreSQL
cd backend
go run ./cmd
```

При локальном запуске `DATABASE_URL` указывает на `localhost`; имя БД и учётные данные должны совпадать с `DB_NAME`, `DB_USER` и `DB_PASSWORD`.

### Способ Б: всё в контейнерах

```bash
docker compose up --build
```

Docker Compose ждёт готовности PostgreSQL и передаёт бэкенду адрес БД по имени сервиса `db`, переопределяя `DATABASE_URL` из `.env`.

При обоих способах приложение подключается к БД через GORM, при включённой настройке обновляет схему и затем запускает HTTP-сервер. Если подключение или миграция не удались, сервер завершится с ошибкой до приёма запросов.

## Проверка

В логе бэкенда должна появиться строка `server started on :8080`.

Откройте в браузере http://localhost:8080/api/health или выполните:

```bash
curl http://localhost:8080/api/health
```

Ожидаемый ответ: `{"status":"ok"}`.

Сборка и проверки из каталога `backend`:

```bash
go build ./...
go vet ./...
```


## Остановка

- Способ А: `Ctrl+C` в обоих терминалах.
- Способ Б: `Ctrl+C`, затем `docker compose down`.
- Остановить и стереть данные базы: `docker compose down -v`.

## Переменные окружения

Файл `.env` не попадает в репозиторий. Шаблон лежит в `.env.example`.

| Переменная | Назначение |
|---|---|
| `PORT` | Порт сервера (по умолчанию 8080) |
| `DB_USER`, `DB_PASSWORD`, `DB_NAME` | Данные для создания базы PostgreSQL в Docker. Используются `docker-compose.yml` |
| `DATABASE_URL` | Строка подключения к PostgreSQL для запуска бэкенда локально (способ А). Значения должны совпадать с `DB_USER`, `DB_PASSWORD`, `DB_NAME`. В контейнере (способ Б) эта переменная переопределяется автоматически |
| `DB_AUTO_MIGRATE` | Обновлять схему при запуске, по умолчанию `true`; `false` отключает миграции |
| `DB_MAX_OPEN_CONNS` | Максимум открытых подключений, по умолчанию `10` |
| `DB_MAX_IDLE_CONNS` | Максимум свободных подключений, по умолчанию `5` |
| `DB_CONN_MAX_LIFETIME` | Срок жизни подключения, по умолчанию `30m` |
| `DB_CONNECT_TIMEOUT` | Таймаут подключения, по умолчанию `5s` |
| `DB_MIGRATION_TIMEOUT` | Таймаут обновления схемы, по умолчанию `1m` |

Реальные ключи и пароли не коммитятся. Общие настройки перечислены здесь; параметры LLM описаны в [едином документе модуля](docs/LLM_MATERIALS.md#настройки). Новую переменную добавляйте в `.env.example` и соответствующее описание.

### Модели GORM и обновление схемы

Модели разделены по секциям: [`users`](backend/internal/models/users) — пользователь и его роль (`User`, `UserRole`), [`topics`](backend/internal/models/topics) — темы, модули и задания (`Topic`, `Module`, `Exercise`), [`llm`](backend/internal/models/llm) — материалы, ответы и очередь LLM (`Material`, `Answer`, `LLMRequest`). Общие перечисления и тип `JSON` находятся в корневом пакете [`models`](backend/internal/models). Секция `llm` использует модели из `users` и `topics` для связей. Подключение и миграции лежат в [`backend/internal/database`](backend/internal/database).

Комментарии описывают связи, nullable-поля, содержимое JSON и ограничения доступа. Приватные поля исключены из JSON-сериализации; бизнес-API использует отдельные DTO из контрактов. Подключение закрепляет схему `public` для моделей и миграций. Разделение моделей по папкам не меняет таблицы БД или API-контракты.

При `DB_AUTO_MIGRATE=true` каждый запуск проверяет модели и применяет дополнения к схеме. Миграция выполняется в одной транзакции PostgreSQL под advisory lock, чтобы несколько экземпляров приложения не меняли схему одновременно. Вместе с `AutoMigrate` устанавливаются индексы, составные внешние ключи и триггеры, которых недостаточно описать базовыми тегами GORM. Для старой общей схемы снимается `NOT NULL` с внутреннего создателя модуля. Подключение или миграция с ошибкой останавливают запуск; некорректные настройки окружения также возвращают ошибку. При завершении приложения пул подключений закрывается.

При добавлении сущности внесите модель в список миграции, а при добавлении поля обновите модель и связанные контракты. Проверьте обновление на отдельной БД. `AutoMigrate` используется для дополнений: переименование, удаление колонок, сложное изменение типа и заполнение старых данных требуют отдельного SQL-скрипта с ревью. Для контролируемого обновления окружения можно отключить автоматическое применение через `DB_AUTO_MIGRATE=false`.

[`docs/schema.sql`](docs/schema.sql) служит справочным SQL для пустой БД. Его не нужно запускать поверх таблиц, созданных GORM. Старый прототип `be3.*` автоматически не переносится.

## Работа с Git

### Ветки

- `main` — стабильная ветка, напрямую в неё не пушим.
- Каждая задача делается в своей ветке от актуального `main`.
- Имя ветки: `тип/номер-задачи-кратко`, только латиница и дефисы.

```
feature/16-auth-api
fix/22-level-calculation
docs/readme
```

Типы: `feature` — новая функциональность, `fix` — исправление, `docs` — документация, `chore` — инфраструктура и мелочи.

```bash
git switch main
git pull
git switch -c feature/16-auth-api
```

### Коммиты

Сообщение в формате `тип(область): что сделано`:

```
feat(backend): add login endpoint
fix(frontend): correct level badge color
docs: update README
```

Один коммит — одна логическая правка.

### Pull request

1. Запушьте ветку и откройте PR в `main`.
2. Заполните описание: что сделано, номер задачи из YouGile, как проверить.
3. Дождитесь зелёного CI.
4. Нужен минимум один review от другого участника. Ревью делаем в течение суток.
5. После одобрения автор PR сливает его и удаляет ветку.

Один PR — одна задача. Большие PR разбиваем на части.

## API-контракты

Текущие маршруты материалов полностью описаны в [`docs/LLM_MATERIALS.md`](docs/LLM_MATERIALS.md). Проектируемые API других частей системы собраны в [`docs/CONTRACTS.md`](docs/CONTRACTS.md). При изменении эндпоинта обновляйте соответствующее описание в том же PR.

Общая схема v0.2: [`docs/DATABASE.md`](docs/DATABASE.md) и [`docs/schema.sql`](docs/schema.sql). Девять таблиц: пользователи, темы, исходные материалы, модули, задания, ответы, очередь LLM, готовые материалы каталога и избранное. При миграции добавляются десять стартовых тем без изменения уже существующих. Каталог отделён от источников для LLM; его HTTP-обработчики будут добавлены отдельно. Модуль заданий хранит название, тему и сложность A1–C2; задания наследуют тему и уровень. Прогресс и личный словарь будут добавлены отдельно.

[`Шаблоны заданий`](docs/exercise-templates.json), [`примеры девяти типов`](docs/exercise-examples.json) и [`OpenAPI v0.2`](docs/be3/openapi.json) согласованы с новой моделью. Визуальные схемы: [`БД`](docs/be3/images/be3-database.png) и [`поток API`](docs/be3/images/be3-api-flow.png). Реализованы приём текстовых материалов, импорт TXT/MD/DOCX, чтение материала и статуса его подготовки по ID. Остальные бизнес-ручки пока описывают будущую реализацию. Старые пути `docs/be3/DESIGN.md` и `docs/be3/schema.sql` направляют к общей схеме.

## LLM и подготовка материала

Модуль принимает английский текст или извлекает его из TXT, Markdown и DOCX, сохраняет материал и определяет CEFR через LLM. Сейчас он временно работает без проверки пользователя: материалы и статусы общие и читаются по ID. Создание самих упражнений ещё не подключено.

Запуск модуля, все параметры LLM, API с примерами, ограничения и карта кода находятся в [едином документе модуля материалов и LLM](docs/LLM_MATERIALS.md).
