# LingoWay

Веб-платформа для изучения английского языка: программы обучения, уроки, база готовых материалов и генерация упражнений по собственному тексту пользователя.

Учебный командный проект по дисциплине «Теория разработки ПО».

## Стек

| Часть | Технологии |
|---|---|
| Бэкенд | Go, Gin, GORM, PostgreSQL, JWT, bcrypt |
| Фронтенд | HTML, CSS, JavaScript, Vite |
| Инфраструктура | Docker, nginx, GitHub Actions |

## Быстрый старт

Сейчас работает запуск бэкенда без Docker.

### Что понадобится

- [Git](https://git-scm.com/)
- [Go](https://go.dev/dl/) версии 1.27 или новее (проверка: `go version`)
- [PostgreSQL](https://www.postgresql.org/) версии 16; доступная БД и пользователь указываются в `DATABASE_URL`

### Запуск бэкенда

```bash
git clone https://github.com/TRPO-project/LingoWay.git
cd LingoWay

# 1. Создать файл с настройками
cp .env.example .env

# 2. Указать подключение к существующей PostgreSQL БД в DATABASE_URL
# 3. Запустить сервер
cd backend
go run ./cmd
```

Перед запуском создайте БД `lingoway` в PostgreSQL и проверьте подключение из `.env`. Приложение подключается к БД через GORM, при включённой настройке обновляет схему и затем запускает HTTP-сервер. В логе должна появиться строка `server started on :8080`.

### Проверка

Откройте в браузере http://localhost:8080/api/health или выполните:

```bash
curl http://localhost:8080/api/health
```

Ожидаемый ответ: `{"status":"ok"}`. Остановить сервер: `Ctrl+C`.

Сборка и проверки из каталога `backend`:

```bash
go build ./...
go test ./...
go vet ./...
```

Интеграционные тесты PostgreSQL включаются переменной `TEST_DATABASE_URL` с адресом служебной БД и пользователем с правом `CREATE DATABASE`. Каждый сценарий создаёт отдельную случайную базу и удаляет только её; исходная БД не меняется. Без этой переменной проверки подключения и миграций на реальном PostgreSQL пропускаются. В CI они запускаются на PostgreSQL 16.

### Переменные окружения

Файл `.env` не попадает в репозиторий. Шаблон лежит в `.env.example`.

| Переменная | Назначение |
|---|---|
| `PORT` | Порт сервера (по умолчанию 8080) |
| `DATABASE_URL` | Обязательная строка подключения к существующей PostgreSQL БД |
| `DB_AUTO_MIGRATE` | Обновлять схему при запуске, по умолчанию `true`; `false` отключает миграции |
| `DB_MAX_OPEN_CONNS` | Максимум открытых подключений, по умолчанию `10` |
| `DB_MAX_IDLE_CONNS` | Максимум свободных подключений, по умолчанию `5` |
| `DB_CONN_MAX_LIFETIME` | Срок жизни подключения, по умолчанию `30m` |
| `DB_CONNECT_TIMEOUT` | Таймаут подключения, по умолчанию `5s` |
| `DB_MIGRATION_TIMEOUT` | Таймаут обновления схемы, по умолчанию `1m` |
| `JWT_SECRET` | Секрет для подписи JWT-токенов |
| `LLM_API_KEYS` | Ключи LLM API через запятую |

Реальные ключи и пароли не коммитятся.

### Модели GORM и обновление схемы

Модели разделены по секциям: [`users`](backend/internal/models/users) — пользователь и его роль, [`topics`](backend/internal/models/topics) — темы, [`llm`](backend/internal/models/llm) — материалы, модули, задания, ответы и очередь LLM. Секция `llm` объединяет подготовку материала, генерацию заданий и проверку ответов; связи с пользователями и темами используют модели соответствующих пакетов. Подключение и миграции лежат в [`backend/internal/database`](backend/internal/database).

Комментарии описывают связи, nullable-поля, содержимое JSON и ограничения доступа. Приватные поля исключены из JSON-сериализации; для бизнес-API нужно использовать отдельные DTO из контрактов. Подключение закрепляет схему `public` для моделей и миграций. Разделение моделей по папкам не меняет таблицы БД или API-контракты.

При `DB_AUTO_MIGRATE=true` каждый запуск проверяет модели и применяет дополнения к схеме. Миграция выполняется в одной транзакции PostgreSQL под advisory lock, чтобы несколько экземпляров приложения не меняли схему одновременно. Вместе с `AutoMigrate` устанавливаются индексы, составные внешние ключи и триггеры, которых недостаточно описать базовыми тегами GORM. Для старой общей схемы снимается `NOT NULL` с внутреннего создателя модуля. Подключение или миграция с ошибкой останавливают запуск; некорректные настройки окружения также возвращают ошибку. При завершении приложения пул подключений закрывается.

При добавлении сущности внесите модель в список миграции, а при добавлении поля обновите модель и связанные контракты. Проверьте обновление на отдельной БД. `AutoMigrate` используется для дополнений: переименование, удаление колонок, сложное изменение типа и заполнение старых данных требуют отдельного SQL-скрипта с ревью. Для контролируемого обновления окружения можно отключить автоматическое применение через `DB_AUTO_MIGRATE=false`.

[`docs/schema.sql`](docs/schema.sql) служит справочным SQL для пустой БД. Его не нужно запускать поверх таблиц, созданных GORM. Старый прототип `be3.*` автоматически не переносится.

## Работа с Git

### Ветки

- `main` — стабильная ветка, напрямую в неё не пушим.
- Каждая задача делается в своей ветке от актуального `main`.
- Имя ветки: `тип/номер-задачи-кратко`, только латиница и дефисы.

```
feature/16-auth-api
fix/22-level-calculation
docs/readme
```

Типы: `feature` — новая функциональность, `fix` — исправление, `docs` — документация, `chore` — инфраструктура и мелочи.

```bash
git switch main
git pull
git switch -c feature/16-auth-api
```

### Коммиты

Сообщение в формате `тип(область): что сделано`:

```
feat(backend): add login endpoint
fix(frontend): correct level badge color
docs: update README
```

Один коммит — одна логическая правка.

### Pull request

1. Запушьте ветку и откройте PR в `main`.
2. Заполните описание: что сделано, номер задачи из YouGile, как проверить.
3. Дождитесь зелёного CI.
4. Нужен минимум один review от другого участника. Ревью делаем в течение суток.
5. После одобрения автор PR сливает его и удаляет ветку.

Один PR — одна задача. Большие PR разбиваем на части.

## Структура репозитория

```
LingoWay/
├── backend/
│   ├── cmd/            # точка входа (main.go)
│   └── internal/
│       ├── config/     # загрузка настроек из окружения
│       ├── database/   # GORM: подключение, ограничения и миграции PostgreSQL
│       ├── httpapi/    # маршруты и обработчики HTTP
│       └── models/     # модели общей БД с комментариями
│           ├── users/  # пользователь и роли
│           ├── topics/ # темы
│           └── llm/    # материалы, модули, задания, ответы и очередь LLM
├── docs/
│   └── CONTRACTS.md    # контракты API: запросы и ответы эндпоинтов
├── .github/workflows/  # CI (сборка и проверки при каждом PR)
├── docker-compose.yml  # Docker-окружение (в разработке, задача №13)
├── .env.example        # шаблон переменных окружения
└── README.md
```

## API-контракты

Формат запросов и ответов каждого эндпоинта описан в [`docs/CONTRACTS.md`](docs/CONTRACTS.md). Бэкенд и фронтенд ориентируются на него, чтобы работать параллельно. Меняете эндпоинт — обновите контракт в том же PR.

Общая схема v0.2: [`docs/DATABASE.md`](docs/DATABASE.md) и [`docs/schema.sql`](docs/schema.sql). Семь таблиц: пользователи, темы, материалы, модули, задания, ответы и единая очередь/журнал LLM. Модуль хранит название, тему и сложность A1–C2; задания наследуют тему и уровень. Публичный автор не требуется: внутренний создатель может отсутствовать у системного публичного модуля и не раскрывается в API. Приватные модули сохраняют владельца для проверки доступа. Прогресс и личный словарь будут добавлены отдельно.

[`Шаблоны заданий`](docs/exercise-templates.json), [`примеры девяти типов`](docs/exercise-examples.json) и [`OpenAPI v0.2`](docs/be3/openapi.json) согласованы с новой моделью. Визуальные схемы: [`БД`](docs/be3/images/be3-database.png) и [`поток API`](docs/be3/images/be3-api-flow.png). Модели GORM и подключение БД реализованы в бэкенде; бизнес-обработчики из контрактов ещё не реализованы. Старые пути `docs/be3/DESIGN.md` и `docs/be3/schema.sql` направляют к общей схеме.
